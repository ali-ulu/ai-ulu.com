# ai-ulu.com — Cloudflare Workers migration

## Scope and safety

This branch stages the migration without changing `main`, the current FTP workflow, production DNS, or the existing mail MX records.

The preview Worker is named `ai-ulu-com-migration` and uses its `workers.dev` URL. No production custom domain is configured here.

## Runtime architecture

```text
Visitor
  |
  v
Cloudflare Edge (HTTPS)
  |
  v
Worker
  |-- POST /form.php -> validate -> D1 (lead + rate limit) -> Email Sending
  |
  +-- all other paths -> Static Assets (shipcraft/dist/)
```

The existing `shipcraft/app.js` sends JSON using these keys:

- `name`
- `reach` (email address OR phone number)
- `type` (`site`, `app`, `both`, or `unsure`)
- `msg`
- `website` (honeypot)

The Worker intentionally preserves this contract. No front-end change is required. It returns a 2xx response after a lead is safely stored in D1 even if the notification email fails; the notification status is then marked `failed` for later inspection.

## Files added

- `wrangler.jsonc` — Workers, static assets, D1 and Email Sending bindings.
- `src/worker.js` — form endpoint, validation, atomic per-IP rate limit, lead storage and email notification.
- `schema.sql` — initial D1 schema.
- `test/worker.test.js` — Node tests for routing, form contract, validation, honeypot, rate limit and email failure handling.
- `package.json` — ESM project metadata and pinned Wrangler version.
- `.github/workflows/deploy-cloudflare-preview.yml` — branch-only verification and opt-in preview deployment.
- `shipcraft/dist/_headers` and `.assetsignore` are generated by `shipcraft/build.mjs`.

The existing `.github/workflows/deploy.yml` (Hostinger FTP) is intentionally unchanged.

## Local verification

Requirements: Node.js 22 or newer.

```powershell
npm install
npm test
npm run build
npx wrangler dev
```

The Node tests use mocked D1 and Email bindings. They do not create remote resources or send real email.

## Configure D1 before a preview deployment

1. Create the D1 database:

   ```powershell
   npx wrangler d1 create ai-ulu-leads
   ```

2. Copy the returned database ID into `wrangler.jsonc`, replacing `REPLACE_WITH_D1_DATABASE_ID`.
3. Apply the schema once to the remote database:

   ```powershell
   npx wrangler d1 execute ai-ulu-leads --remote --file=schema.sql
   ```

Do not run this schema command on every deploy. The schema is an initial migration, not a deployment step.

## Configure Email Sending

1. In Cloudflare Email Service, onboard `ai-ulu.com` for outbound Email Sending.
2. Authorize `noreply@ai-ulu.com` as a sender.
3. Confirm `aliulu@ai-ulu.com` is an allowed destination for the Email Sending binding.
4. Verify the Email Service DNS records. Keep exactly one SPF record at the domain root; merge provider mechanisms if the dashboard requires a combined SPF value.

Email Sending is outbound notification from the Worker. It is separate from Email Routing, which handles inbound forwarding to Gmail. Do not replace the current MX records just to deploy the website.

## GitHub preview deployment

Add repository Actions secrets:

- `CLOUDFLARE_API_TOKEN`
- `CLOUDFLARE_ACCOUNT_ID`

The workflow first builds and tests the site. Preview deployment is opt-in: set repository Actions variable `CLOUDFLARE_PREVIEW_ENABLED=true` only after the D1 ID and Email Service onboarding are ready. Until then, the workflow verifies the branch without deploying.

The workflow deploys only the migration Worker to `workers.dev`; it does not attach `ai-ulu.com` or `www.ai-ulu.com`.

## Preview acceptance checks

At the generated `workers.dev` URL, verify:

- `/` and `/tr/` load.
- `/about/`, `/contact/`, legal pages and `/templates/` load.
- `/robots.txt`, `/sitemap.xml`, `/llms.txt`, Markdown alternates and the MCP Server Card are served.
- Static requests never expose `form.php`, `.htaccess`, or `leads/**`.
- The contact form accepts an email address and a phone number.
- A successful form submission creates one D1 lead.
- A bot-filled `website` honeypot does not create a lead or send email.
- The sixth submission within the configured 15-minute IP window receives HTTP 429.
- Email delivery failure leaves the D1 lead stored with `notification_status='failed'`.

Do not send real test messages to the production inbox until the preview Worker and Email Sending configuration have been reviewed.

## Production cutover — separate approval gate

Only after preview acceptance:

1. Add `ai-ulu.com` and `www.ai-ulu.com` as Custom Domains on the intended production Worker.
2. Confirm Cloudflare has provisioned the custom-domain DNS records and TLS certificate.
3. Replace the Hostinger A records only as part of that reviewed custom-domain cutover. Do not delete records blindly.
4. Preserve inbound mail records until Email Routing to Gmail has been separately configured and tested.
5. Confirm the site's form endpoint and all static paths on the custom domains.
6. Keep the Hostinger FTP workflow and old deployment available until the new production site has passed acceptance.

## Data migration notes

The migration does not automatically import any old JSONL lead files from Hostinger into D1. Export and import those records separately if they are available. It also does not restore Hostinger mailboxes or old email messages.
